## 3 第二轮 故障恢复与验收可执行性

方法：读取第一轮修订后的数据、运行时、发布与验收章节，沿正常保存、保存后应用失败、在途请求、撤销、崩溃、升级、满盘及恢复路径走查；检查每条编号需求是否有用例、是否引用尚未交付的能力，以及文档渲染与链接是否准确。

| 编号 | 严重程度 | 输入中的问题与影响 | 修订位置与结果 |
| --- | --- | --- | --- |
| R2-01 | 高 | DATA-02写“应用失败继续旧快照”，也笼统覆盖凭据变更；重启还允许从最近可用旧配置启动，可能恢复用户撤销的凭据或停用目标 | DATA-06、第6.6节、A27：安全撤销单独持久记录，限制覆盖旧快照，确认绑定实例；新实例默认最新配置，失败不自动回退；旧配置恢复不解除撤销 |
| R2-02 | 高 | RUN-06承诺协议版本不兼容时仍可编辑配置，与DATA-04禁止旧程序写新schema冲突 | RUN-06、A04/A23：只有schema受支持时可编辑；不支持时只给诊断和受控恢复 |
| R2-03 | 高 | 凭据先写、配置后提交虽有清理描述，但创建凭据后崩溃可能没有可恢复记录，无法区分本次孤儿与用户已有秘密 | DATA-03、A03：先记录操作ID和唯一待创建引用；恢复仅处理明确属于本应用且未使用的引用，清理失败可重试 |
| R2-04 | 高 | 只要求更新壳与网关，没有排除CLI或其他入口在迁移期间继续写库，存在不一致和回滚丢数据风险 | REL-03、A23：排他维护锁，协调所有入口；无权停止独立实例则暂缓；迁移后新写入先保全并说明再恢复 |
| R2-05 | 高 | 请求数据只有按天保留，无容量上限，也没定义磁盘满时请求能否继续和计数是否完整 | OBS-06、第6.6节、A28：容量/期限双约束；派发前登记失败拒绝新请求；结束写失败降级；未知结果显式记录，有限恢复队列 |
| R2-06 | 中 | first_cloud规定5分钟健康过期，但没有复检机制和费用边界，可能持续不可用或自动发起收费探测 | 第9.2节、A14：真实成功刷新健康时间；有限低成本探测；无合适端点时要求显式试调用；连通/模型存在/推理成功分开 |
| R2-07 | 中 | P0的A05要求“CLI实例连接”，正式CLI却在P3交付，验收依赖再次倒置 | A05及第17节说明：P0用测试驱动启动真实独立进程验证所有权，正式CLI仍在P3验收 |

第二轮结果：上述8项均已修订，并补入A27/A28和相应出口条件。复核了受影响章节，确保没有把安全撤销与普通配置替换混用，没有要求P0提前交付P3 CLI，也没有通过删除验收规避问题。
