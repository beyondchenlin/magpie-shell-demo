# SUP-007：撤销确认与派发准入屏障

2026-10-18（Asia/Shanghai）。本记录只闭环监督指出的 DATA-06 派发竞态，**不代表 A27 或 P1 整体通过**。全程为隔离无窗口测试，未控制桌面、读取窗口、重装或访问真实密钥/上游。

## 确定性失败

验证前，在真实本机 HTTP 请求的策略检查已成功、尚未开始发送目标步骤时，通过 test-only hook 暂停。持久撤销 `cancel_inflight=false`，等待对应运行状态确认修订，再释放请求。

原始 `evidence/SUP-007-before.txt` 显示首步及顺序小队的后续步都发生 **目标上游调用 1 次、HTTP200**，测试失败。不能用“中间步骤已经到达上游后撤销”的既有测试代替此窗口。验证前源码 hash 绑定于 before-source.json，两个原始源文件快照按字节保留为 before-security-source.txt / before-http-source.txt。快照只含源码和合成测试，非用户资料。

## 修复与线性化点

`Gate::confirm` 和 `Run::admit_dispatch` 使用同一个 Tokio mutex。原有配方/步骤检查只作为预检；真正派发时在该屏障内重读持久安全策略，并在同一临界区内创建、首次轮询 `request.send()`。随后立刻释放屏障，等待上游响应头/正文时不持锁。因此确认不能越过一个尚未开始发送的请求，也不会等待已经开始的请求全部完成。

这里的派发准入线性化点是屏障内启动 HTTP 发送 future；没有声称字节已经到达远端。确认之前已经启动的请求属于在途，`cancel=false` 允许它完成；确认完成之后尚未准入的首步/后续步都必须被新策略拒绝。没有用追加一次无同步检查、取消所有在途、忽略用户的取消选择或网络重放来修复。

手动目录 GET 也采用相同准入与发送首轮询屏障；六秒总预算包含准入等待。安全/预算不满足时不启动网络操作。安全存储读取许可跟随真实阻塞 worker，读失败、超时或不一致按未确认处理，不用空策略放行。

## 最终验证

原始 `SUP-007-all-scopes.txt` 及最后 `P1-S10-gateway-final.txt` 覆盖：

- 供应商连接撤销：检查后暂停的首步/后续步，确认后释放均为 **目标调用0、403**。
- 本机访问令牌撤销：相同首步/后续步窗口，同样为 **目标调用0、403**。
- 屏障内部暂停的已准入请求：测试确认 mutex 确被持有，撤销确认 future 在释放前不能完成；启动发送后确认才返回。`cancel=false` 下该请求 **调用1、200**，之后的新请求被拒绝，未取消全部在途来掩盖竞态。
- `SUP-007-inflight-regression.txt` / `P1-S10-security-http-final.txt` 的真实独立 sidecar：已经到达上游的中间步骤可以完成，但已撤销的最终步骤不会派发；实例确认、目录过滤、重启及旧 UUID 保护继续通过。
- 真实 HTTP + 内存凭据验证 `cancel=true` 关闭受控上游，保留已有流片段并返回 ACCESS_REVOKED，不输出成功 DONE；该测试不接触 OS 凭据库。不存在“false 一律取消”的实现。

固定测试钩子仅 cfg(test) 编译，生产无此等待。重复执行不累计为新增用例。before/after/final 原始输出与源码绑定均保留；源码最终指纹见 after-source.json 和 P1-S10-manifest.json。
