# Tagma 产品需求文档 v0.3

Tagma 为个人用户提供统一的模型供应商管理、本机路由网关和按需安装的专家队员。用户可以从已有 Agent 调用，也可以逐步使用 Tagma 内置对话。桌面应用负责管理，同一套 Rust 核心支撑网关、CLI 和后续 MCP 入口。

本版将已有 CIS 成果转化为正式产品开发依据：前端继续使用 React、TypeScript 和 Vite，桌面迁移到 Tauri 2，网关作为 Rust sidecar 与桌面同包分发。交付遵循先可靠地基、再真实网关、再一个队员验证的顺序。

## 1 产品目标与成功标准

### 1.1 用户问题

多个 Agent 分别管理供应商、模型和 Key，用户需要重复配置，发生错误时难以判断原因。本地爬取、音视频等能力通常需要单独安装运行环境，也缺少一致的调用和维护方式。

Tagma 将供应商、组合小队与专家队员汇聚到本机入口。用户安装一个应用即可管理网关，重型能力按需安装。默认安装包不包含大参数本地对话模型，不要求用户预装 Python、Node.js、Rust 或 Docker。

### 1.2 目标

| 编号 | 用户结果 | 成功信号 |
| --- | --- | --- |
| G1 | 一处管理供应商，供多个客户端使用 | 修改配置后可看到保存和生效状态，重启不丢失 |
| G2 | 外部 Agent 经本机网关调用模型 | 无需打开内置对话，即可完成声明支持的流式请求 |
| G3 | 组合小队作为可选模型使用 | 发布的小队出现在 models 列表，并能被真实调用 |
| G4 | 专家队员按需安装 | ReachFlow 安装、试跑、调用与卸载有完整结果 |
| G5 | 普通用户能够恢复故障 | 错误指出原因类别和可执行下一步，不伪装成功、不无限重试 |
| G6 | 多入口共享能力 | Skill、MCP、CLI 与桌面使用同一核心契约 |
| G7 | 后续可内置 Agent | Pi 系 harness 的模型调用经网关，特权工具有独立授权 |

### 1.3 统计与衡量

阶段验收采用第 17 节固定用例，关键路径及安全边界用例必须全部通过，不用平均通过率掩盖失败。发布后观察首次配置成功率、首次真实请求成功率、异常退出、恢复耗时与安装失败原因。分母、时间窗口和排除上游故障的规则必须随统计说明给出。

默认不上传用户行为和请求内容。初期指标来自本机诊断及经用户同意导出的脱敏记录；未来如增加遥测，须单独说明采集字段、用途、保存时间及关闭方式。

## 2 用户与核心使用场景

| 用户 | 要完成的事 | 主要入口 |
| --- | --- | --- |
| 个人 Agent 用户 | 多个 IDE/CLI 共用供应商、模型和用量 | 供应商、接入向导、本机 API |
| 内容与研究用户 | 安装 ReachFlow 等能力并用于任务 | 队员市场、小队、试跑 |
| 终端与自动化用户 | 不依赖窗口运行调用流程 | CLI、MCP、Skill |
| 仅使用 Tagma 的用户 | 对话和调用能力 | 对话；真 Agent 为后续交付 |
| 未来团队运维者 | 局域网服务、访问控制与用量 | P4 服务器版 |

首个真实闭环是：添加供应商 → 检测 → 保存并生效 → 获取接入信息 → 外部客户端发送请求 → 查看结果与用量。队员和内置 Agent 均不得成为这个闭环的前置依赖。

## 3 已确认边界与建议变更

### 3.1 沿用的产品约束

1. 默认三页为对话、供应商、队员市场；组合小队从市场进入，运维能力放二层。
2. React + TypeScript + Vite + CIS 保留；Tauri 2 提供桌面宿主，Rust 提供业务核心与独立网关。
3. 桌面与网关为两个业务程序，同一安装包交付；WebView 等系统辅助进程不计作业务架构数量。
4. 先个人桌面；macOS 优先首发，Windows 紧随，Linux 按对应平台验收后发布。当前 Windows 开发验证不更改首发策略。
5. Skill、MCP、CLI 对等调用同一运行时；可修改 Base URL 的客户端使用声明支持的 HTTP API。
6. 地基顺序为壳、网关、队员契约、ReachFlow。TTS、ASR、字幕、剪辑、财务和文档队员属于插件积压需求。
7. Pi 系内置 Agent 为独立长线，脑经过网关；不整仓移植 PI-Desktop，不从零再造完整 Agent 执行器。
8. 沿用经过验证的视觉与交互；组件择优复用，耦合严重的页面业务逻辑可重写。不会因迁移 Tauri 自动获得旧 Electron 验收结果。
9. 外部 Agent 会话以只读方式导入历史快照；继续对话时创建 Tagma 自己的 Pi 会话，后续消息、工具执行与状态只属于 Tagma，不修改、续写或同步回原 Agent 会话。此项为用户于 2026-10-18 明确确认的产品行为，按独立内置 Agent 切片交付。

### 3.2 本版建议变更

下表是针对旧冻结要求的显式修订提案。开发可实现相应机制和两种策略的测试；对外发布前由负责人确定产品行为，不能把提案记作已经获得批准。

| 决策 | 旧版 | 本版建议 | 影响与决定时点 |
| --- | --- | --- | --- |
| DEC-01 本机鉴权默认值 | 个人版默认关闭 | 正式发行默认生成本机访问令牌；无鉴权仅显式兼容模式 | 接入向导增加令牌步骤；P1 发布前确认，未确认时不默改旧默认，也不将开发配置称为发行默认 |
| DEC-02 小队名称冲突 | 重名与配方版本都使用 @n | slug 在本机唯一；重名拒绝并建议新 slug；@n 仅用于配方修订 | 避免调用对象歧义；小队发布功能开发前确定，基础存储与校验可先实现 |
| DEC-03 P0 真实性 | 三页主路径允许假后端 | P0 供应商 CRUD、排序、持久化和网关生命周期真实；模型推理尚未完成时明确未接入 | 提高 P0 出口标准；mock 保留在独立演示入口，不作为正式运行结果 |

性能预算、保留期限和恢复上限在本文中是拟采用的产品要求，不是已有实测结果。实现设计需落实到配置默认值和测试，不允许为了凑通过而临时放宽。

## 4 范围与交付阶段

| 阶段 | 必须交付 | 不计作本阶段完成条件 |
| --- | --- | --- |
| P0 原生底座与主路径 | Tauri 三页、CIS 接入、真实配置服务与凭据存储、受管 sidecar、诊断、安装验证；演示模型目录仅独立预览 | 真实推理、真实队员安装、Pi 循环 |
| P1 网关与组合 | 至少一种协议的真实流式链路；供应商连通检测、模型目录、小队 CRUD 与发布、手动/顺序策略、用量 | 任意 Agent 全兼容、全部协议、真实内容队员、复杂计费 |
| P2 队员契约 | manifest、校验、安装事务、权限、进程隔离、ReachFlow 试跑与路由、更新/卸载 | 同时交付一批音视频或财务队员 |
| P3 多入口与对话扩展 | 官方 CLI、Skill 和 MCP 实际调通至少一个队员或小队；外部客户端接入完善 | 必须交付完整 Pi 生态 |
| P4 服务器版 | 同核心无界面服务、Docker Compose、局域网鉴权、按 Key 用量、部署与恢复说明 | 多租户 SaaS、充值发票体系 |

内置 Pi Agent 在 P1 网关稳定后单独立项，可以与后续阶段按资源安排推进；不能通过它延期 P0–P2。队员安装器和服务器版的后台框架不提前引入主程序。

### 4.1 Desktop 与 Web 边界

个人桌面版执行本机网关、凭据存储和队员。Web 默认是独立演示预览，不启动本机进程，不读取桌面密钥或配置。将来如提供远端管理，须作为独立认证与部署范围验收，不能直接把桌面管理命令暴露到公网。

P0 演示目录至少包含一个上游云模型名、一个官方 tagma/ 队员示例、一个用户小队示例；与真实 /v1/models、生产目录和用量完全隔离。可见预览不计作真实运行验收。

### 5.2 外观和组件要求

UI-01：沿用 CIS 的 token、行与卡片节奏、按钮、开关、分段选择、弹窗和菜单。产品三页 IA 优先于复刻版全导航；原生桌面窗口与 Web 预览模拟框分别处理。

UI-02：控件进入产品组件库前验证 props/类型边界、键盘和焦点、关闭与卸载、窄窗口、长文本、明暗主题及禁用/忙态。产品代码不得依赖 comparison 查询参数或演示存储键获得正常业务行为。

UI-03：至少覆盖当前支持的中英文；已有日文、德文、繁体中文在迁移中不无声丢失。新增译文未完成的语言标记覆盖状态，关键动作不得显示原始翻译 key。状态信息同时有文字，不依赖颜色。支持系统减弱动态效果，字体缩放后不遮挡提交或取消。

UI-04：每个异步操作有加载、成功、失败、取消和重试行为。成功以后台确认结果为准；取消界面等待与取消后台任务分别告知。隐藏在其他页面的操作通过任务/状态入口可查询，不能在卸载后弹出无对应任务的成功提示。

新产品不以六份 CSS 永久字节一致作为唯一质量标准。旧 cis-guard 保留用于复刻基线；产品规则变更必须更新对应规格、影响范围和回归用例，不能单纯关闭 guard。

## 6 核心用户流程

### 6.1 首次启动与供应商接入

1. 应用加载本机配置。没有供应商时显示真实空态；sidecar 可处于“运行中，未配置模型”，不生成假可用模型。
2. 用户选择供应商类型，输入地址和凭据，选择适用 App 配置。界面说明检测可能访问该供应商。
3. 保存前做本地格式校验。检测返回连接、鉴权、模型可用性等独立状态；P0 没有上游检测时按钮明确不可用。
4. 保存成功返回配置版本；随后显示应用到网关的结果。网关不可用时仍可保存，提示“已保存，待生效”。
5. 用户复制地址、模型 ID 与访问令牌，通过接入向导配置外部客户端。敏感令牌的显示和复制是用户显式动作，日志不记录内容。
6. 发起真实请求后，用量页出现相同 request_id 的记录；上游没有 token 数据时显示未知。

### 6.2 修改配置与恢复

用户编辑供应商 → 本地/后台校验 → 事务保存新版本 → 网关验证完整快照 → 一次性切换有效版本 → 新请求使用新版本。在途请求保持既有版本。应用失败保留旧有效版本，界面同时显示已保存与运行中版本，并提供修正和重试。

### 6.3 小队配置与发布

市场进入组合小队 → 新建草稿 → 选择脑、成员和策略 → 校验依赖 → 展示公开模型 ID → 发布 → 进入 models → 试跑 → 查看版本与用量。缺成员、无可用脑或策略不支持时允许保存草稿，但不能发布为可用模型。

### 6.4 队员安装与卸载

打开详情 → 查看来源、权限、平台、下载和安装峰值空间 → 用户确认 → 下载并校验 → 暂存安装 → 健康检查 → 注册能力。取消或失败不修改当前可用版本。

卸载前展示受影响小队和在途任务，允许取消；确认后先停止接收新任务，再等待或取消在途任务，解除注册并删除该版本运行文件。用户输出单独保留，是否删除须另行选择。

### 6.5 网关故障

状态页说明失败类型、时间和最近可用版本。壳仍可编辑供应商。可恢复崩溃执行有限重试；配置错误、权限错误、端口冲突直接提示修复，不无限循环。用户可导出脱敏诊断，不需要复制完整日志目录。

### 6.6 关键错误与恢复动作

| 情形 | 用户看到的结果 | 允许的下一步 |
| --- | --- | --- |
| 端口被占用 | PORT_IN_USE，原服务与配置保持 | 用户选择新端口并重新配置客户端，或处理已知占用程序 |
| 凭据库不可用 | CREDENTIAL_STORE_UNAVAILABLE，不显示保存成功 | 解锁/修复凭据设施，重试本次保存 |
| 并发编辑 | CONFIG_CONFLICT，保留尚未提交的编辑 | 查看差异、刷新后重做，不盲目覆盖 |
| 配置尚未生效 | CONFIG_APPLY_FAILED，显示两个 revision | 修正或重试；安全撤销走专门路径 |
| 无可用脑 | NO_AVAILABLE_BRAIN | 检测/配置供应商或显式选择合格模型 |
| 不支持能力 | UNSUPPORTED_CAPABILITY | 修改请求或选择已支持协议/模型 |
| 用量不可持久化 | USAGE_STORAGE_UNAVAILABLE，网关降级 | 释放应用自身可回收空间/修复存储，恢复后再接新请求 |
| 版本/schema不兼容 | INCOMPATIBLE_VERSION，不执行危险读写 | 使用兼容版本或受控恢复，不强制降级写库 |

这些是内部稳定错误类别；HTTP适配器将其映射到所声明协议的状态码和错误结构，用户文案独立本地化，禁止直接显示含秘密的原始异常。

## 7 供应商与 App 管理

| 编号 | 需求 | 规则 |
| --- | --- | --- |
| PROV-01 | 创建、编辑、启用、停用、删除、排序 | 供应商 UUID 稳定；删除前列出引用，不能遗留无提示的失效小队 |
| PROV-02 | 连接与模型检测 | 分开显示格式错误、DNS/网络、TLS、超时、401/403、限流、协议不支持、模型不可用；记录检测时间 |
| PROV-03 | 按 App 管理 | App 配置引用供应商，不复制 Key；全局默认序明确可见，App 覆盖不暗中改全局序 |
| PROV-04 | 模型目录 | 保留上游 ID；支持发现与显式配置来源标记；缓存标记检测时间，不假定发现列表保证调用成功 |
| PROV-05 | 安全存储 | 密钥写入凭据存储，前端回读仅脱敏和存在状态；凭据不可访问时不降级明文 |
| PROV-06 | 客户端接入 | 给出协议、地址、模型和鉴权说明；按已测试客户端版本发布兼容矩阵 |

App 配置优先提供复制和指导；后续自动改写外部 Agent 配置必须先展示目标文件与差异，获得确认，检测文件是否并发修改，并支持定向恢复。禁止扫描并导入其他应用的登录凭据。OAuth 仅对已实现且验证的供应商开放，其余不得显示模拟登录成功。

## 8 网关与协议契约

### 8.1 服务与兼容范围

GW-01：网关为独立 Rust 程序，默认绑定 loopback。开发/测试用端口由独占配置指定；用户正式配置端口被占用时不自动换端口，使客户端仍指向旧地址。

GW-02：P1 首个协议为 OpenAI Chat Completions 的明确子集：GET /v1/models、POST /v1/chat/completions，含非流式、SSE 流式、错误返回与已声明的工具调用转发。Responses、Anthropic、Gemini 是独立适配与验收项，未实现时返回明确不支持，不声称 Codex/Claude Code 等必然可用。

GW-03：models 仅列出已启用、完成发布且具备运行依赖的对象。响应遵循所声明的兼容格式；显示名、来源、健康状态等额外管理信息通过管理接口提供，不依赖第三方客户端解析自定义字段。

### 8.2 请求执行

GW-04：请求绑定 request_id、配置版本、模型/配方版本和实际目标。流式解析不得按网络 chunk 假定一个完整事件；处理分片、多事件、UTF-8 边界、结束帧和异常断流。未声明的功能字段按兼容策略拒绝，不能静默删除而改变任务语义。

GW-05：区分连接超时、首个响应超时、流空闲超时和总任务预算，允许按供应商配置。断开客户端应触发上游取消并停止继续消费内容；不能把“用户已关闭页面”自动解释为所有外部调用都取消。

GW-06：设请求体、并发、队列和缓冲上限，队列满时返回可识别错误。慢客户端产生背压，不把完整响应无限积压在内存。默认不对生成请求透明重试；只有能证明尚未派发，或上游明确支持幂等且符合预算时才能重试。已经输出内容、执行工具或结果不确定时不自动换渠道重放。

GW-07：网关本身不执行云模型返回的任意工具调用。普通兼容转发将 tool_calls 交回调用方；仅小队/队员运行时执行其已授权契约内的操作。每次外部副作用需要明确的执行归属。

### 8.3 入口访问控制

GW-08：数据 API 与管理操作分离。模型调用令牌不能启停进程、修改供应商或安装队员。管理接口不挂在可选无鉴权的 /v1 路由下。桌面管理走受限 Tauri 命令及本机私有 IPC。

P1 必须测试鉴权开启和显式关闭两种模式：开启时缺失/错误令牌返回 401；关闭仅允许本机绑定，不能据此开放局域网。DEC-01 决定正式默认值。令牌可以轮换和撤销，已撤销令牌不接受新请求。

禁止将 CORS 当作访问控制；检查 Host/Origin、拒绝默认浏览器跨站访问和不受信任的管理请求。对 loopback、本机私有 IPC 和同用户进程攻击的能力边界须如实说明，不能承诺抵御已控制用户账户的恶意软件。

## 9 模型 ID 与组合小队

### 9.1 名称与版本

TEAM-01：云模型保持上游公开 ID；Tagma 自有官方队员和用户小队使用 tagma/ 前缀。API slug 为 2–64 个 ASCII 字符，同时满足完整匹配 `^[a-z0-9]([a-z0-9-]*[a-z0-9])?$` 与长度限制；展示名允许中文。前缀由系统写入，不可删除。

官方保留名至少含 reachflow、local-brain；保留名注册表随产品版本维护，不允许新的保留名静默覆盖现有用户对象。冲突必须阻止发布并给出迁移说明。多个供应商提供同名云模型时，models 去重，目标按有效配置中的全局优先序及显式策略确定，管理页展示可选来源。上游 ID 占用 tagma/ 命名空间时标记冲突，不能静默改名或覆盖自有模型。

TEAM-02：草稿可修改；发布配方形成不可变修订。public_id、display_name、内部 UUID 和修订号分开存储。DEC-02 推荐 slug 唯一、@n 只表示版本。已被调用方固定使用的 ID 不悄悄指向语义不同的配方；删除或停用显示影响范围。

DEC-02 推荐规则下：首个发布版本的公开 ID 为 tagma/<slug>，永久绑定修订 1；修订 2 起使用 tagma/<slug>@2、@3 等。不提供自动漂移的 latest 别名，不把修订 2 覆盖到原裸 ID。修改草稿不影响已发布版本；调用不可用或已停用版本返回明确错误。models 列出启用且可执行的已发布版本，客户端迁移由用户明确选择。草稿不提供可调用公开 ID。

### 9.2 脑选择与策略

| 编号 | 模式/策略 | 规定 |
| --- | --- | --- |
| TEAM-03 | first_cloud | 按全局供应商序，再按供应商模型序，选已启用、最近检测连通且支持所需能力的云模型；无全局序时采用明确选定的默认 App 配置序 |
| TEAM-04 | explicit / local_brain_pack | explicit 固定供应商 UUID 与模型；Local Brain 仅在已安装且健康时可选；v0 不开放 none |
| TEAM-05 | manual / sequential | P1 必有手动固定目标和顺序步骤；每步明示输入来源、输出用途、超时、失败策略与可见副作用；失败默认中止，不把未知结果当成功 |
| TEAM-06 | intent | 后续能力；只有单独定义意图规则、确定性回退、预算与测试后才开放 |

first_cloud 默认检测有效期 5 分钟；过期进入待复检，不能永久复用陈旧“可用”。没有合格渠道时返回 NO_AVAILABLE_BRAIN，引导用户配置，不暗装本地大模型。运行中选定的脑保持不变；后续请求可重新按新有效配置选择。

近期真实调用成功可以更新其实际模型能力的健康时间；后台复检只使用供应商声明支持且无需生成计费内容的检测方式，并有频率上限和退避。没有合适检测端点时显示需要手动试调用，不自动发起可能收费的生成请求。供应商连通、模型存在和真实推理成功分开记录，models接口成功不等于所有模型已通过推理。复检失败不触发用户请求的静默重放。

每个配方包含内部 ID、公开 ID、修订号、展示名、brain、members/steps、routing、权限和状态。发布时检查循环依赖、缺失版本、步骤输入输出、能力兼容及最大执行预算。配方权限是各步骤所需权限集合，不能因为组成小队而获得额外权限。

### 9.3 P1 与 P2 的执行依赖

TEAM-07：步骤目标有明确类型：cloud_model 引用供应商 UUID 和模型 ID，pack 引用已安装队员及契约兼容的固定版本。P1 只执行 cloud_model 步骤，以云模型组合作为真实小队验证，不依赖尚未实现的 ReachFlow 安装器；包含 pack 的草稿在 P2 依赖就绪前不能发布。Local Brain 未安装时同样不能作为 P1 的隐含前提。

manual 在执行前确定一个目标；sequential 为有序步骤，P1 输入只允许原始用户消息和显式指定的上一步文本结果，最终步骤构成对外回答。中间结果不混入最终回答流；中间步骤必须产生可消费的文本，不能含未处理 tool_calls。最终步骤的 tool_calls 可按普通转发契约返回外部客户端。P1 不执行任意脚本、自动工具回环或小队递归；后续增加能力要新增契约和验收。

在用户要求 stream 时，只流式输出最终步骤，等待中间步骤受整队截止时间约束；尚未产生输出时失败返回标准错误，流已经开始后失败按声明的流错误语义结束，不偷偷重跑前面步骤。整队取消向所有活动步骤传播；未执行步骤不得继续启动。

## 10 队员市场与运行时

PACK-01：队员最小 manifest 包含 ID、版本、官方/社区来源、支持平台与架构、入口协议、运行命令、资源需求、下载信息与校验、权限、健康检查、模型公开方式、兼容契约版本。安装包内不得含指向任意外部目录的不可控安装脚本路径。

PACK-02：安装前计算下载、解包、现用版本和切换暂存的峰值空间；检查系统临时盘与目标盘。对压缩包路径穿越、符号链接逃逸和解压大小设限制；空间不足时说明缺口，不移动到另一个同样不足的盘继续。

PACK-03：官方清单必须有可信来源和可验证签名，内容 checksum 同时匹配。仅有同一不可信下载站提供的 checksum 不足以证明发行者身份。校验失败停止，不提供默认跳过选项。

PACK-04：安装和更新在私有暂存目录完成，验证通过才切换活动版本；运行中的任务绑定旧版本，结束后再回收可重建文件。崩溃或重启后可识别未完成事务，恢复或回滚，不留下“显示已安装但无法调用”的半状态。

PACK-05：队员在独立进程运行，有并发、超时、取消、资源和日志边界。子进程隔离不等于安全沙箱；权限声明必须映射到可执行的限制，无法约束的能力需准确披露，不能将勾选框宣传成系统强制隔离。

PACK-06：P2 仅以 ReachFlow 验证完整契约。用户的研究预算、目标平台限制、登录、确认和浏览器授权继续由 ReachFlow 服务执行，Tagma 不代为绕过。试跑默认采用本地固定测试素材；真实采集是单独明确动作，可取消并返回任务 ID、状态与输出位置。

PACK-07：队员输出写入用户选定工作目录；运行缓存、下载缓存和用户成果分开。卸载运行文件不会删除用户成果。第三方社区队员在其信任与权限流程完成前不开放执行。

## 11 对话与多入口

CHAT-01：P0 展示真实未接入状态和供应商引导；开发预览可演示，但有持续可见的演示标识，使用独立存储命名空间。P1 之后的基础对话通过本机网关发送、流式展示、停止与报错，不建立第二条直连云 API 的路径。

CHAT-02：Pi 系 Agent 为后续独立工作包，须定义 first-send、prompt、followUp、abort 与会话恢复契约；不依赖旧文档中未定义的 SessionDaemon 实现名称。管理供应商、队员和小队的特权工具使用单独授权与确认，模型生成的指令不构成用户确认。请求结果中的网页、文件和工具文本均不得改变本机权限。

ENTRY-01：CLI、MCP、Skill 共用 Rust 业务契约，不各自实现路由、存储和鉴权。P3 验收至少包括列出 models、调用一队员或小队、查询状态、取消任务。CLI 可在没有桌面窗口的情况下连接现有网关；启动网关时明确进程所有权和配置目录。

ENTRY-02：普通 MCP 面只暴露调用能力。安装/卸载、供应商修改等特权控制不自动对所有外部 MCP 客户端开放。Skill 是薄调用说明与配置，不内嵌用户密钥；提示词默认仅本机存储；会话内容与用量元数据采用不同保留策略。

### 11.1 读取外部会话并在 Tagma 内继续（已确认，待实现）

用户价值：用户可以将其他 Agent 已积累的对话背景带入 Tagma，直接由内置 Pi 接续工作，不必手工复制整段历史。交付归属为 CHAT-02 的独立内置 Agent 工作包，前提是 Pi 循环与会话持久化可用；不改变先 P0、真实 P1、ReachFlow P2、P3 的主线顺序，也不将现有基础对话描述为已实现 Pi。

CHAT-03：用户从二层“会话”入口选择受支持的外部 Agent 和会话，预览历史后执行“在 Tagma 中继续”。读取必须只读，形成截至导入时刻的历史快照，并生成新的 Tagma 会话 ID。界面持续区分“导入的历史”和“Tagma 中的新对话”，保留来源 Agent、源会话标识和导入时间。此操作不启动或恢复原 Agent，不改写其记录、索引、标题、分支、删除状态或运行状态，也不建立双向或后台同步；原会话后来新增的内容不会自动进入 Tagma。再次导入作为新的独立会话处理，不能静默合并或重复追加。

CHAT-04：新会话由 Tagma 内置 Pi 执行，模型调用遵守 CHAT-01，经本机网关使用 Tagma 配置的供应商与模型。用户在 Tagma 中发送消息、停止、关闭重开、重命名或删除会话，只影响 Tagma 自己的数据；原 Agent 会话继续独立存在。导入保留可理解的用户/助手消息与工具结果，历史仅作为上下文，不自动重放工具调用、挂起任务或未完成请求，不继承原 Agent 的登录凭据、系统权限或工具授权。源记录中的系统/开发者指令和工具文本不得升级为当前会话的高优先级指令；新的工具操作遵守 Tagma 的权限与确认契约，工作目录在新会话中明确展示，导入文件路径本身不授予目录访问权。

CHAT-05：按实际验证的 Agent、版本和记录格式发布兼容矩阵，不承诺任意会话无损接管。导入前展示支持的消息/附件类型、遗漏项与上下文截断或摘要策略；超出限制、损坏、不支持、源记录读取期间变化或附件缺失时给出明确结果，不将不完整内容伪装为完整导入。适配器不导入认证字段或秘密配置，对历史中识别出的密钥脱敏并提示用户检查预览；发送给模型只发生在用户开始新对话之后。读取、解析及持久化有大小、时间和事务边界；失败或取消不留下可见的半导入会话，也不触及源数据。Tagma 重启后从自己的会话存储恢复，不依赖原文件仍存在。

用户流程：选择来源与会话 → 只读加载并预览导入范围、遗漏和来源 → 点击“在 Tagma 中继续” → 创建独立 Pi 会话并显示所用模型/工作目录 → 用户发送新消息 → 新结果只存入 Tagma。该流程是历史上下文迁入后的新会话，不宣称恢复原 Agent 的隐藏推理、内部执行状态或未完成工具调用。

## 12 数据与配置一致性

### 12.1 核心实体

| 实体 | 关键字段和约束 |
| --- | --- |
| Provider | UUID、名称、协议、Base URL、credential_ref、启用、排序、模型序、能力、检测结果与时间 |
| AppProfile | UUID、目标 App 类型、引用供应商、覆盖配置、全局默认标记 |
| ConfigRevision | 递增 revision、schema_version、不可变配置内容及credential_ref、校验结果、提交时间；不含秘密；有效版本另记 |
| TeamRevision | UUID、slug、公开 ID、不可变修订、脑/成员/策略、权限、draft/published/disabled |
| PackInstall | pack_id、版本、平台、来源签名、校验值、权限、安装状态、活动版本 |
| RequestRecord | request_id、上游 attempt_id、目标与版本、状态、时间、token 来源、错误分类 |
| RuntimeInstance | instance_id、协议/程序版本、配置目录标识、启动方式、状态、地址、有效 revision |
| ChatSession / ImportedHistory | 新 Tagma session_id、来源 Agent/格式版本/源会话标识、导入时间、历史快照、导入消息边界、遗漏/摘要说明、新消息及 Pi 状态；存于 Tagma 自己的会话存储，源位置仅为来源信息，不是写入或同步目标 |

DATA-01：统一 Rust 配置服务执行校验和事务写入，Tauri 与 CLI 使用同一实现；数据库并发采用 SQLite 事务和 expected_revision 乐观锁。网关读取不可变快照，不直接改业务配置。过期编辑提交返回冲突，不能覆盖其他客户端更新。

这里的配置服务是共享 Rust 应用服务，不要求另起常驻配置进程。多个本机入口通过同一写入实现和事务并发控制访问；数据库迁移须持排他迁移锁并协调所有入口。配置与请求用量分库，网关写用量库，避免遥测写入变成业务配置修改。网络探测和凭据交互不在长时间 SQLite 写事务内进行。

DATA-02：配置保存与网关生效是两步；保存成功返回 desired_revision，网关确认后更新 effective_revision。应用失败不撤销已保存编辑，也不伪造生效；新请求使用旧有效快照直到替换成功。供应商凭据变更同样遵循此规则。

保存后的通知只是加速同步；网关启动、管理通道重连和周期核对均读取持久 revision，恢复丢失通知。有效版本属于具体 runtime instance，不以数据库中的历史确认代替本次握手。新实例默认加载最新保存版本；校验失败时停止启动，不自动回退到可能恢复已停用供应商或撤销凭据的历史版本。用户可显式选择兼容的历史配置恢复，但恢复始终叠加当前安全撤销状态，并产生新的 revision。

DATA-03：凭据存储与 SQLite 不是同一个事务。写新凭据引用、提交配置，再延迟回收旧引用；数据库提交失败清理本次未引用凭据。崩溃恢复检查暂存记录和引用状态，不删除仍被有效配置或在途请求使用的凭据。导出默认只含非敏感配置，不含 Key、访问令牌、会话正文。

在创建新凭据前先持久记录本次操作 ID 与待创建的唯一引用；创建完成后再提交配置关联。恢复只清理有本应用操作记录、确认未被引用且不在使用的凭据，不按名称批量扫描/删除用户凭据。清理失败保留可重试状态，不把成功保存的配置当作失败重复创建。

DATA-04：数据库迁移必须版本化、校验和可恢复。迁移前做一致性备份；失败保留原库和诊断。不得直接复制运行中的 SQLite 主文件而忽略 WAL。旧程序遇到不支持的新 schema 必须拒绝写入并给恢复路径，不能宣称所有升级都支持直接降级。

DATA-05：从 demo 导入只允许显式选择的非敏感偏好；comparison Agent、假供应商、假检测和演示用量不导入生产数据。保留旧安装与资料可回看，但不共享可写配置目录。

DATA-06：普通配置替换与安全撤销不同。用户明确撤销令牌/供应商凭据或紧急停用目标时，写入持久撤销记录；运行实例确认禁止新的派发，再按用户选择取消在途任务。撤销限制覆盖旧有效快照及尚未执行的小队步骤，历史配置恢复不能解除撤销。

只有收到对应 runtime instance 的确认才能显示“运行中已撤销”。通信失败显示“撤销已保存，运行中未确认”，提供停止本应用拥有的网关或指导用户停止独立实例；不能擅自终止他人进程。已经发送给上游的请求只能尝试取消，可能已发生费用或副作用，不能承诺撤销追溯消除结果。

### 13.1 代码职责

| 层 | 职责 | 禁止承担的职责 |
| --- | --- | --- |
| React + CIS | 展示、受控输入、交互状态 | 执行任意 shell、直接写数据库、保存长期凭据、私自推导运行成功 |
| Tauri Rust 宿主 | 原生窗口/托盘、限定命令、配置服务入口、进程管理 | 复制一套网关路由或用量逻辑 |
| 共享 Rust 核心 | 领域规则、配置、契约、错误、权限判定 | 依赖 DOM 或 Tauri 窗口才能运行 |
| Rust 网关 | HTTP 数据面、供应商适配、请求生命周期、用量 | 信任任意前端命令、伪造协议兼容、直接修改业务配置 |
| 队员运行时 | manifest 安装与子进程管理 | 将社区代码加载进壳主进程 |

ARCH-01：技术路线为 React + TypeScript + Vite + CIS、Tauri 2、Rust。网关建议采用 Tokio + Axum/Tower，存储采用 SQLite；具体依赖版本在实现时核对并锁定。核心不要求终端用户安装开发工具链。

ARCH-02：跨边界命令具备版本、类型、校验、稳定错误码、超时及取消语义；共享 DTO 单源生成 TypeScript 类型并在 CI 检查漂移。管理 IPC 使用 Named Pipe/Unix Domain Socket 等本机私有通道，校验当前用户权限、实例身份和协议兼容性，不只信任 PID 或可猜测路径。

### 13.2 生命周期

RUN-01：状态为 stopped、starting、running、degraded、stopping、failed。spawn 成功不等于服务可用；只有端口绑定、配置装载和身份握手完成才进入 running。没有供应商是可运行的空配置，不列出假模型。

RUN-02：每用户/配置目录一个活动网关，使用原子锁与实例握手解决并发启动；PID 仅为诊断字段。已有兼容实例可连接但不自动获得停止权限；版本不兼容提示更新/显式迁移。端口属于其他程序时不终止它，也不暗改客户端地址。

RUN-03：关闭窗口保留托盘和网关；“退出 Tagma”默认退出壳并优雅停止自己拥有的网关，先说明活动请求。由 CLI 独立启动或外部拥有的实例不随壳退出。Mac 无窗口但应用仍运行与完全退出分别处理。支持的无托盘环境必须保留明确的运行/退出入口。

RUN-04：启动等待上限建议 10 秒；失败显示具体阶段。崩溃自动重启建议最多 3 次/5 分钟，延迟 1、2、4 秒；配置、权限、身份或端口错误不自动重试。用户手动重启先重新验证条件，不叠加多个重启循环。

RUN-05：停止先停止新请求，再等待活动任务，默认等待 10 秒；超过后按用户已选择的退出行为取消并回收本实例拥有的进程。壳异常退出时，被它拥有的普通 sidecar 应通过平台进程约束/父进程存活机制退出；独立启动模式不受此影响。进程树和管道回收须在目标平台实际验证。

RUN-06：管理通道和日志分离，不能依赖解析任意 stdout 文本控制进程。状态事件可重连恢复，按快照与事件序号同步；前端丢事件不能永久显示旧状态。程序和协议版本不兼容时拒绝运行操作；只有本机配置 schema 仍受支持时才允许编辑，不支持的 schema 不作写入，仅展示版本诊断与受控恢复入口。

## 14 非功能与安全要求

| 编号 | 需求 | 可验收要求 |
| --- | --- | --- |
| NFR-01 | 体验响应 | 本地点击反馈目标 ≤100ms；耗时操作立即出现忙态且可查询，不等待网络完成才反馈 |
| NFR-02 | 启动 | 在登记的参考设备上，20 次冷启动可交互时间 p95 ≤3 秒；网关就绪另计，上游检测不阻塞窗口 |
| NFR-03 | 网关开销 | loopback 测试上游、并发 10、1000 请求，网关附加首包延迟 p95 ≤30ms；排除上游推理并报告失败与取消 |
| NFR-04 | 资源有界 | 并发、输入体积、队列、流缓冲、任务时长和解压大小都有配置上限；稳定负载运行 30 分钟无持续线性内存增长 |
| NFR-05 | 日志 | 脱敏结构化日志，默认单文件 ≤20MiB、最多 5 份；不记录 Key、访问令牌或完整请求/响应正文 |
| NFR-06 | 可访问性 | 主路径全键盘可达，焦点清晰、关闭回焦、屏幕阅读器标签与错误关联、减弱动效；100%/125%/150%缩放可操作 |
| NFR-07 | 信任边界 | 窗口仅获必要能力，远程网页不获本机特权；本机命令做业务校验；正式包无任意 shell/调试后门 |
| NFR-08 | 网络与隐私 | TLS 证书校验开启；自定义企业 CA 有显式配置，不提供“关闭所有校验”默认修复；上游地址变更不带原 Authorization 跨源重定向 |

以上数值是工程验收目标，需要在实现设计中登记 CPU、RAM、操作系统、WebView 和构建模式。Mac 与 Windows 各自测试，不能拿 Vite 浏览器结果代替桌面结果；参考设备尚未登记时不得宣布性能通过。

秘密存储在支持的平台凭据设施中，不可用或锁定时提示解锁/配置，绝不自动回退到 localStorage、明文 JSON 或日志。Linux 无桌面凭据服务与未来服务器版使用单独设计的秘密提供方式，不把个人桌面方案硬套到无界面环境。

子进程 crash isolation、文件系统权限和沙箱隔离是不同承诺。产品展示只使用已实际实现和验证的能力名称。涉及执行第三方代码、覆盖外部 Agent 文件、敏感导出或删除用户成果时必须有具体操作确认。

## 15 用量与诊断

OBS-01：记录按供应商、模型、小队与修订聚合的请求数、成功、失败、取消、等待/执行耗时和可获得 token。区分用户逻辑请求与上游尝试次数；未知 token 不记为 0，不把估算费用当供应商账单。

OBS-02：用量有时间范围、时区、刷新状态和错误筛选；用户可检查 request_id、目标、配置版本与错误码。默认保存 30 天请求元数据、12 个月日汇总，可调或清除；清除前显示范围，清除后不从旧缓存自动恢复。默认不保存正文；会话正文如启用须单独说明保留和删除方式。

OBS-03：诊断包包含版本、平台、进程状态、配置 schema/revision、脱敏错误和有限日志。用户预览后导出；不打包整个数据库、凭据库、个人文件或浏览器资料。遥测默认关闭。

OBS-04：发布说明区分技术测试、平台安装、真实服务与用户体验验收。旧 CIS 27/0/2、Electron 九项回归和 v208 安装证据只覆盖原候选，不作为 Tauri 或新产品已通过的依据。

OBS-05：P1 提供按供应商/模型/小队的周期汇总与简易额度展示。用户设置的软预算与上游真实余额区分；缺少价格或 token 时显示未知，不绘制虚假余额。实际计费信息可用时注明来源与更新时间，额度条分母为已知额度；无额度时显示用量。默认不承诺硬金额封顶；如启用请求数/token硬限制，须定义并发预留、结算和超限拒绝，用量估算不能承诺不会超额收费。

OBS-06：请求元数据还受本机容量上限约束，默认用量库目标上限 256MiB，先到期限或容量条件者触发按既定保留策略清理；先完成日汇总再清理旧明细，界面标记明细起始时间。WAL、索引、备份与日志单独计入峰值空间，不把数据库文件大小当全部物理占用。

请求派发前持久登记开始记录；写入失败则拒绝新派发并进入降级，不无限排队或静默丢账。结果写入失败时停止接收新请求并保持有限恢复队列；重启后将未终结记录标为 interrupted/结果未知，未知token不补零。进程崩溃可能无法拿到上游最终用量，这一限制必须在统计中可见。P4 如增加计费结算须另行设计账务保证。

## 16 构建 发布与恢复

REL-01：保持现有 npm 锁文件与包管理器，增加 Cargo workspace/lock 和明确 Rust 工具链。锁定输入和构建命令，在对应 OS CI 构建；发布物记录源码 SHA、依赖锁、目标平台、程序/协议/schema 版本及哈希。不将开发机路径或配置带入安装包。

REL-02：Tauri 与网关版本作为同一发行单元，sidecar 按目标架构命名并打包，安装后验证它来自当前包。正式 macOS 发行进行所需签名与公证，Windows 进行代码签名；更新包另做签名校验。没有签名条件时产物只能标内部测试，不称正式发行。

REL-03：更新前检查包身份、架构、协议/schema兼容性及可用空间；处理活动请求后更新壳与网关，失败不留下可运行的混合版本。验证重启与配置恢复；如迁移不可逆，提供明确恢复流程，禁止旧二进制直接写新 schema。

每配置目录的更新/迁移持排他维护锁，阻止新入口启动或写入；先与所有已连接入口和活动实例协调，再替换二进制或迁移。独立启动且本壳无权停止的实例仍占用时，更新暂缓并说明操作方式。迁移失败恢复一致备份；如发生过迁移后的新写入，回退必须先保全并展示会丢失的变更，禁止无提示覆盖。

REL-04：安装、升级、卸载均说明用户配置和成果去向。默认卸载程序保留用户数据，清除数据为独立选择。旧 Electron 比较版和 Tagma 使用不同应用身份与配置目录。

REL-05：构建前检查目标盘与 Temp、已有缓存与运行环境。预计新增 >1GiB 时记录目录、峰值、复用和回收方案，保留至少 10GiB 余量；相关盘 <20GiB 优先复用，<10GiB 暂停预计新增 >1GiB 操作。任务缓存与交付物分开，测试数据由 finally/teardown 清理。不得删除旧证据或其他任务产物。

2. 输出架构决策记录：配置与秘密事务、IPC契约、进程所有权、模型兼容范围、迁移与更新策略。为 DEC-01–03记录决定，不重复要求已确认的技术选型。
3. 完成 P0：Tauri 原生窗口、CIS基础交互、配置服务、sidecar管理、真实状态、平台安装。A01–A07通过，发布涉及的A23–A25通过。
4. 完成 P1：先一条供应商真实流式链路，再小队和用量；A08–A16及A27/A28通过，至少一个外部客户端具备版本绑定证据。未支持的App不进入兼容名单。
5. 完成 P2：ReachFlow完整安装到调用闭环；A17–A20通过后再安排其他队员。
6. 完成 P3 与独立对话切片（Pi 循环、持久化及外部历史导入后独立续聊，A22/A29），再按需求进入 P4。任何阶段只交付通过对应验收的能力，不能把可点的按钮当业务已完成。

各阶段使用单一进度清单，逐项标记未开始、实现中、验证中、通过、失败、外部条件阻塞。审查未通过的关键问题必须修复或明确缩小发行范围；不能通过改名或删验收消除失败。排期在完成环境盘点和架构基线后估算，旧版周数不作为当前交付承诺。

## 19 风险与发布依赖

| 风险/依赖 | 应对与边界 |
| --- | --- |
| 复刻代码与模拟逻辑耦合 | 逐组件审查，建立统一服务接口；必要时重写业务层，保留经过验证的视觉 |
| 真实协议兼容范围过宽 | 先锁端点/字段/客户端版本矩阵；新增协议单独验收 |
| 网关与界面互相牵连 | 进程独立、业务核心无窗口依赖、离线配置与版本快照 |
| 密钥存储或更新半完成 | 明确跨存储提交/恢复顺序，故障注入验证 |
| sidecar/队员进程残留 | 平台生命周期验证，所有权校验，有界退出与恢复 |
| Mac/Windows签名与构建条件 | 正式发布前落实账号/证书/目标机器；本地编译不冒称平台发布完成 |
| 社区队员执行权限 | 可信来源先行、权限如实展示，隔离未实现前不开放不受信任执行 |
| 上游或ReachFlow服务条件 | 错误分类、预算与取消；不把外部授权失败改成假成功 |
| 不断增加复刻差异 | 产品范围以本PRD为主，旧复刻问题独立留账 |
| 存储与证据膨胀 | 复用缓存、有限日志和必要证据，遵守本机磁盘约束 |

## 20 非目标与需求变更

个人版首期不包含大模型服务器、预装大本地模型、Docker依赖、P2P/Swarm、复杂SaaS计费、移动原生App、所有供应商OAuth、任意Agent自动接管、未实现的系统沙箱承诺。不会整体改用C++，不会将React替换成另一框架来掩盖业务边界问题。

需求变更必须说明用户价值、受影响阶段、行为变化、迁移和新增验收。发布前冻结对应版本的范围与协议；未确认提案不覆盖旧已确认行为。新增内容队员不占用地基阶段关键路径，Pi长线不成为网关可用的前提。
